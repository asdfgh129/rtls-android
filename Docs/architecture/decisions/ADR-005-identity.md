# ADR-005：用户与设备身份模型

- 状态：Accepted
- 日期：2026-10-19
- 关联：[初始方案（归档）](../../archive/plan-2026-10-17.md) 3.4、4.2

## 背景

现有文档混用了“用户”和“设备”：

- 协议消息里带 `deviceId`；
- 数据库只有 `devices`；
- 好友关系直接连 `device_id`；
- 没有说明一人多设备、换机、账号恢复如何处理。

如果直接把设备当用户，短期简单，但换机后好友关系、历史轨迹、分享设置都会丢失或需要迁移。

## 决策

采用 **`users` + `devices` 两层模型**：

- `users`：账号身份，承载好友关系、分享开关、好友码。
- `devices`：安装实例，承载位置、Token、在线状态。
- 好友关系建立在 **user 级**。
- 位置数据建立在 **device 级**。
- MVP 默认一人一设备，但模型支持一人多设备。

### 关系

```text
users 1 ─── n devices
users n ─── n users   (friendships，规范化存储)
users n ─── n users   (friend_requests / blocks)
devices 1 ─── n locations
devices 1 ─── 1 device_latest
```

### 授权规则

查询/订阅某台设备的位置，必须同时满足：

1. 请求方设备已认证且 `status = 'active'`；
2. 目标设备存在且 `status = 'active'`；
3. 目标设备所属用户 `share_enabled = true`；
4. 请求方用户与目标用户是好友；
5. 双方不存在任何拉黑关系。

服务端从 JWT 解析 `deviceId/userId`，忽略客户端消息体中的身份字段。

### 设备策略

- `devices.is_primary`：每个用户最多一台主设备，用于默认展示；
- 好友默认看到主设备位置；后续可扩展“分享哪些设备”；
- 换机：新设备注册后设为主设备，旧设备可撤销；
- 历史轨迹按 `device_id` 查询，好友查询主设备历史。

## 理由

- 换机、重装、账号恢复不会丢好友关系。
- 好友码/拉黑/分享开关属于账号级，不应该复制到每台设备。
- 位置是设备级事实，保留 `device_id` 有利于多设备区分。
- MVP 一人一设备时，API 仍然简单：`deviceId` 从 `/v1/me` 获取。

## 后果

### 正面

- 数据模型可演进，不需要在换机时迁移好友关系。
- 权限判断有明确的主体（user）和客体（device）。
- 未来支持“手机 + 平板”或多设备分享时不需要重构。

### 负面 / 需要注意

- 所有查询都需要 join `devices → users → friendships`，SQL 稍复杂。
- 需要维护“主设备”唯一性（部分唯一索引）。
- 客户端需要理解 `userId` 与 `deviceId` 的区别。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 设备即用户（只有 `devices`） | 不采用 | 换机丢关系；后续迁移成本高 |
| 用户即设备（一个用户只能一台设备） | MVP 可行但不采用 | 模型锁死，扩展性差 |
| 组织/群组层级 | 暂不采用 | 当前是好友互查，不需要组织模型 |

## 验证方式

- 数据库约束测试：同一用户只能有一个 `is_primary = true`。
- 授权矩阵测试：非好友、被拉黑、目标关闭分享、目标设备撤销，全部返回 `FORBIDDEN`。
- 换机流程测试：新设备注册为主设备后，好友查询到新设备位置。
